# 日报新仓旧仓动作与空仓语义收口

状态：📋 PRD 已完成，待后续实现

## Goal

让日报把“明日不新增参与”“已有旧仓如何处理”“何时要求账户归零”分别写清，避免把新仓 0% 误写成账户已经空仓，也避免市场偏弱时机械提前卖掉仍有独立强势的旧仓。

## User Story

- **角色**：使用固定交易窗口、希望减少盘中盯盘的 A 股短线交易者。
- **场景**：日报给出明日新仓 0%，但账户可能有已确认旧仓、前日报待成交计划，或持仓事实尚未输入。
- **目标**：在开盘前知道是否不买、是否在上午退出旧仓、是否只做一次 10:10 复核，以及收盘前账户应保留多少仓位。
- **成功标准**：用户不需要从“空仓”一词猜测买卖含义；日报、持仓策略、HTML 和验收检查对同一账户事实给出一致动作。

### 用户旅程

1. 日报先给出明日新仓比例，不用它反推已有持仓。
2. 系统核对旧仓事实，区分已确认、待成交确认、明确无旧仓和持仓未输入。
3. 对已确认旧仓，区分已经失败、待 10:10 复核和正常存活三类。
4. 已失败旧仓在 `09:50-10:10` 完成退出；待复核旧仓只在该窗口检查一次，三层承接成立才保留到 `14:30-14:55`；正常 T+2 样本按尾盘预案退出。
5. 报告写明收盘目标仓位；窗口外不生成临时动作。

## What I Already Know

- 当前候选与仓位结论中的 `0%不参与`主要表达不新增参与，不能证明账户已有持仓为零。
- 当前日报可能同时写“持仓未输入”和“账户风险暴露 0x”，这是不可同时成立的账户事实。
- 现有 `.trellis/spec/backend/daily-report-decision-loop.md` 已定义 `old_position_plan.v1`，但代码尚未形成统一的结构化旧仓动作产物。
- 现有正式买卖窗口仍是 `09:30-09:35`、`09:50-10:10`、`14:30-14:55`。
- `13:45-14:10` 只作日终与 replay 研究，不新增人工查看或临时卖出。
- 2026-07-13 长电科技说明“市场差就开盘立即卖”不成立，也说明板块与指数同步恶化可以使旧仓从独立强势转为退出样本。
- 用户还经历过早盘退出后旧仓尾盘创日内高点甚至涨停的反例；该反例要求保留“10:10 三层承接成立则允许尾盘处理”的成功路径，不能用单一案例把所有旧仓改成上午清仓。

## Requirements

- [ ] R1: 日报账户动作必须分开输出明日新仓比例、旧仓事实、旧仓判断、旧仓动作和收盘目标仓位，不再用单独的“空仓”同时代替这些结论。
- [ ] R2: 复用并落实 `old_position_plan.v1`，对已确认旧仓至少区分 `已经失败`、`待10:10复核`、`正常存活`；对待成交确认、明确无旧仓和持仓未输入保持独立事实，不得视为已确认旧仓。
- [ ] R3: 已经失败的旧仓使用 `09:50-10:10` 作为最后退出窗口；待复核旧仓在同一窗口核对个股相对昨收/分时均价、相对指数强弱和板块核心同步承接，条件成立才允许继续到 `14:30-14:55`，否则在 10:10 前退出。
- [ ] R4: 正常 T+2 样本仍按 `14:30-14:55` 退出；没有明确 T+2 或旧仓生命周期事实时，不伪造 T+2 身份或精确退出结论。
- [ ] R5: 持仓未知时，账户风险暴露和收盘目标仓位必须写待确认；前日报计划待成交确认时必须保持 0x，且不得生成旧仓卖出动作。
- [ ] R6: 日报首页、明日执行结论、账户日序表、持仓策略和 Bear HTML 必须使用同一账户动作含义；最终新仓 0% 可以与正常存活旧仓并存，不视为结论冲突。
- [ ] R7: LLM Wiki 必须记录新仓与旧仓分离、三类旧仓动作、10:10 三层复核、尾盘例外和事后涨停不能反推当时动作对错。
- [ ] R8: 验收检查必须拒绝“持仓未输入但风险暴露为 0x”“已确认旧仓但只写不新增参与”“待成交计划被写成旧仓卖出”“上午清仓却没有 10:10 前动作”等矛盾。
- [ ] R9: 候选生成、`selection_workflow` 最终对象、评分、B1/B2、明日新仓仓位计算和一分钟市场语言研究结论不得因本任务改变。

## Non-functional Requirements

### 兼容性

- 现有结构化持仓事实优先；历史快照只有旧文案时允许保守兼容，但必须显式标记证据不足，不得从模糊文本制造确定动作。
- Markdown 与 Bear HTML 保持相同顺序和含义，窄屏展示不得横向溢出。

### 可追溯性

- 旧仓动作必须保留证据来源；没有分钟、板块或指数事实时不得声称三层复核已经通过。
- 所有 Python 命令使用 `.generated/venv-py314/bin/python3.14`。

## Acceptance Criteria

- [ ] AC-R1-1: 给定最终新仓 0% 且已确认旧仓，日报同时显示“明日新仓 0%”和独立旧仓动作，不显示“账户已经空仓”。
- [ ] AC-R1-2: 给定最终新仓 0% 且明确无旧仓，日报显示无已确认旧仓，收盘目标仓位为 0%。
- [ ] AC-R2-1: 给定旧仓已出现买点失败、失效或明确必须卖证据，结构化计划判为已经失败，尾盘退出不再作为默认动作。
- [ ] AC-R2-2: 给定旧仓证据矛盾但未确认失效，结构化计划判为待 10:10 复核，不直接写上午必卖或继续持有。
- [ ] AC-R2-3: 给定旧仓逻辑仍成立且有明确 T+2 计划，结构化计划判为正常存活并保留尾盘退出。
- [ ] AC-R3-1: 待复核旧仓只有在个股、指数相对强弱和板块同步承接事实齐全且成立时，才允许把退出延后到 `14:30-14:55`。
- [ ] AC-R3-2: 三层事实不成立时，日报要求可卖旧仓在 `09:50-10:10` 完成退出；没有新增 `13:45-14:10` 人工动作。
- [ ] AC-R4-1: 没有持仓周期事实时，日报写“按原预案/待确认”，不自行声称该仓是 T+2。
- [ ] AC-R5-1: 持仓未输入时，风险暴露和收盘目标仓位均为待确认，不得显示 0x 或无持仓负担。
- [ ] AC-R5-2: 前日报计划待成交确认时显示 0x，只核实成交记录，不出现卖出旧仓或尾盘退出动作。
- [ ] AC-R6-1: 同一输入在完整版、摘要版、持仓策略和 Bear HTML 中的新仓比例、旧仓事实、旧仓动作与收盘目标一致。
- [ ] AC-R7-1: Wiki 给出“早盘卖后尾盘涨停”作为必须保留的反例，并明确单次结果只进入复盘，不倒灌当时判断。
- [ ] AC-R8-1: 验收检查对 R8 所列四类矛盾分别返回稳定错误代码。
- [ ] AC-R9-1: 接入前后 `selection_workflow`、`final_target_resolution.new_entry_target`、明日执行对象、明日新仓比例和 B1/B2 逐字段一致。
- [ ] AC-R9-2: 2026-07-13 replay 只改账户动作表达，不改变最终无新增参与对象的结论。
