### Daily Report HTML Surface Selection

The daily report has two different HTML surfaces. Do not choose the target
template from the file name alone.

- Bear / Markdown reader HTML uses `scripts/report/markdown_report_html.py`,
  `scripts/templates/daily_report_markdown_reader.html`, and
  `tests/test_daily_report_markdown_html.py`.
- Structured dashboard HTML uses `scripts/report/html_report_view.py`,
  `scripts/templates/daily_report_reader.html`, and the `test_daily_report_html_*`
  tests.
- Before changing a chart, first confirm the renderer and template pair by
  searching for the chart key, such as `data-bear-chart` for Bear charts or the
  structured dashboard chart id for dashboard charts.
- If the request mentions Bear HTML, Markdown reader, or the report reading
  view, update the Bear / Markdown reader path only. Do not add a duplicate
  chart to `daily_report_reader.html`.
- In the Ta-Te account day-order view, the asset shown for Te comes from the
  Markdown execution-target cell. An empty target stays `无`; account notes must
  never supply a fallback stock.
- The Ta-Te account day-order view keeps the `轨道` and `标的` header/body
  columns visible during horizontal scrolling. The timeline table must override
  the generic table `overflow: hidden`, and both fixed columns must use explicit
  widths matching their sticky offsets.
- The Bear `成交额Top30` chart keeps turnover as the bar length and renders each
  stock's signed change percentage at the bar end. Change percentage must not
  be available only inside a hover tooltip; limit status may follow the visible
  percentage as a secondary label.
- Badge and day-intent parsing must process negative/pending language before
  matching bare `B1` or `B2`. An explicitly external pending-trade row shows
  `只核实` and `空仓执行`, never `参与权` or `确认权`. A prior report's inherited
  tomorrow target is different: on the next trading day it renders as a
  confirmed 50% / 1x simulated old position and may render B1/old-position
  actions.
- For the account day-order date intent, the Te cell owns Te semantics. Positive
  B1/B2 text retained in a historical Ta/Tb/Tc cell must not override Te text
  such as `待成交确认` or `确认已成交才视为B1`. An explicit `B1参与权` in the Te
  cell remains a positive execution plan.

### Market Language Research Evidence Surface

- `## 市场语言翻译（研究证据）` is an evidence section, never an action section.
  It appears after `## 明日执行结论` and after final object resolution.
- The normal report renders range, direction, phase, event quality, counter-
  evidence, and the low-attention target / current-notification limit. Formula
  rankings, AICc tables, and posthoc returns stay in replay/research output.
- The research target limits routine proactive viewing to `T+1 09:30-09:35`
  for the T0-approved B1 and `T+2 14:30-14:55` for the T0 exit plan.
  `09:50-10:10` may only review a T0-approved B2, but the current report does
  not provide an automatic intraday notification; without an explicit prompt,
  B2 is not executed. `13:45-14:10` is extracted only in end-of-day/replay
  research and creates no prompt or temporary action.
- This evidence-surface rule does not claim that the existing formal action
  sections have completed the same migration. Those sections keep their
  current decision inputs until a separately verified strategy change.
- User wording distinguishes `仅见重叠斜率连续` from price directional
  follow-through. It must not describe overlapping windows as confirmed account
  identity or confirmed program-trading causality.
- Structured event times are filtered to the artifact's current direction. If
  only opposite-direction events exist, render them as counter-evidence and do
  not fall back to the timeline's unfiltered first/latest timestamps.
- The research HTML labels the 20-minute value as a rolling-slope curvature
  proxy, shows its formula, and rounds only for display. It must not describe
  that value as a separate quadratic-regression coefficient.
- Every shade on the three historical case charts is a same-day T0 research
  sample. The chart must not relabel those shades as future T+1/T+2 actions or
  as a completed B2 notification. On narrow screens, long inline code wraps
  while tables and charts scroll only inside their local wrappers; the page
  itself has no horizontal overflow.
- `reports/research/quant-pressure-replay-study-20260711.html` is generated by
  `scripts/research/quant_pressure_one_minute_study.py`. A regression test must
  compare the checked-in HTML with generator output exactly.

## Testing Requirements

<!-- What level of testing is expected -->

- Render a prior report's inherited tomorrow target as confirmed actual 1x,
  while keeping Te's new-entry target empty when the current final object is
  empty and retaining the old-position action separately.
- Render an explicitly external pending-trade row as actual 0x and assert its Te
  row contains no participation/confirmation badge.
- Assert historical positive B1/B2 text and Te pending-confirmation text can
  coexist without turning the Te date intent into participation.
- Assert historical unknown-position text cannot turn an explicit Te B1 plan or
  explicit Te empty-account instruction into pending confirmation.
- Render an explicit tomorrow-empty account table, remove one required action
  from the Bear table only, and require acceptance to reject the HTML even when
  the same phrase still exists in later report evidence.
- Assert the day-order timeline table allows sticky overflow and fixes the lane
  and asset header/body cells to their declared widths.
- Assert the Top30 chart payload preserves positive and negative change values,
  and the bar-label formatter renders the signed percentage directly.
- Run acceptance with a deliberately mismatched Bear Te asset and require a
  stable target-conflict finding.
- Assert the market-language heading is classified as evidence and follows the
  formal action heading in Markdown and Bear HTML.
- Render a current upward artifact containing only downward events and assert
  no downward candidate/confirmation time appears under the upward heading.
- Render the Revision 5 research HTML at desktop and 390px widths; assert no
  page-level horizontal overflow, visible T0 sample shades, and nonoverlapping
  lunch-boundary labels.

## Scenario: Bear Tomorrow-Action Calendar

### 1. Scope / Trigger

- Trigger: rendering the recent tomorrow-action review calendar in Bear /
  Markdown reader HTML.

### 2. Signatures

- Renderer:
  `render_markdown_report_html(..., tomorrow_action_calendar=None)`.
- File renderer:
  `render_markdown_report_file(..., tomorrow_action_calendar=None)`.
- Payload schema: `tomorrow_action_calendar.v1`.

### 3. Contracts

- Insert the calendar before the first `.position-timeline-shell`; if the
  timeline is absent, keep the calendar as the first report-body block.
- Render five weekday columns from Monday through Friday. Every populated cell
  shows execution date, weekday, active account legs, each leg's `1x/50%`
  weight and first/second holding day, source report date, daily account return,
  and excess return versus the Shanghai Composite.
- `empty`, `no_new_entry`, `target`, and `incomplete` are distinct visual and
  text states. Future performance says `待发生`; missing historical facts say
  `事实不足`.
- A concrete target participates for two actual trading days at `1x/50%` per
  day. Different overlapping targets render as two separate `1x/50%` rows;
  repeated plans for the same stock render as `2x/100% · 第1+2日`.
- A no-new-entry decision does not erase a prior target's second-day leg. Show
  the active leg and a separate `本日计划：不新增` note. Only an explicit
  tomorrow-empty decision clears all legs; if no active leg remains, render the
  account result as `空仓` while retaining the no-new-entry plan label.
- Fill structural weekday gaps with explicit notes: known holidays show the
  holiday name and `非交易日`, records outside the sample range show `样本外`,
  and only an in-range missing database row shows `记录缺失`. Notes do not
  count as report records or performance days.
- The summary distinguishes target-plan days from account-holding days and also
  exposes valid, empty, no-new-entry, incomplete, and future counts; average
  daily and excess return; cumulative account, Shanghai, and excess return; and
  outperforming-day count.
- Cumulative plan and Shanghai returns are compounded independently over only
  complete records. `cumulative_excess_shanghai_pct` is the cumulative plan
  return minus the cumulative Shanghai return. Do not sum daily excess
  percentage points, and do not include future or incomplete records as zero.
- The component may scroll horizontally on narrow screens. The document itself
  must keep `scrollWidth == clientWidth`.
- Escape every database-derived label before inserting it into HTML.

### 4. Validation & Error Matrix

- Payload absent -> render no calendar and preserve existing HTML output.
- Empty payload -> render the calendar heading plus PostgreSQL fact-incomplete
  text, without an empty table.
- Complete target record -> render signed weighted daily account and excess
  percentages.
- No-new-entry record with a prior second-day leg -> render that leg, calculate
  its `0.5`-weighted return, and keep the no-new-entry plan note separate.
- No-new-entry record without any active leg -> render account return `0.00%`
  when the Shanghai open-to-close fact is complete.
- Any active leg or Shanghai open-to-close fact missing/conflicting -> render
  `事实不足` and exclude the entire day from averages and cumulative values.
- Future execution date -> render `待发生` and exclude it from performance
  totals.
- Narrow viewport -> local calendar scroll is allowed; page-level horizontal
  overflow or clipped cell text is a failure.

### 5. Good/Base/Bad Cases

- Good: 25 records render as a stable five-column trading-week table above the
  account day-order timeline, with visible compounded account, Shanghai, and
  excess values.
- Good: two different stocks show two `1x/50%` rows; same-stock overlap shows
  one `2x/100% · 第1+2日` row with both source report dates.
- Base: eight database records render as eight cells and disclose `8/25` rather
  than inventing the missing dates.
- Bad: a missing stock quote displays `0.00%`.
- Bad: the calendar is appended below the account timeline or makes the entire
  390px page horizontally scrollable.

### 6. Tests Required

- Unit test calendar order, five weekday headers, two active legs, same-stock
  overlap, no-new-entry carry, signed percentages, HTML escaping for every
  database label, empty-source output, and all summary labels.
- Unit test cumulative excess with a sample where simple addition and
  compounding differ.
- Browser verification at 1440x900 and 390x844 asserts component order, 25
  cells, no text overlap, no page overflow, local horizontal scrolling, and a
  fully viewable final cell.

### 7. Wrong vs Correct

#### Wrong

```python
cumulative_excess = sum(record["excess_shanghai_pct"] for record in complete)
```

Daily percentage-point excesses do not preserve the compounded path.

#### Correct

```python
plan_nav *= 1 + daily_return_pct / 100
shanghai_nav *= 1 + shanghai_return_pct / 100
cumulative_excess = (plan_nav - 1) * 100 - (shanghai_nav - 1) * 100
```

This compares cumulative plan and benchmark performance over the same complete
records.
