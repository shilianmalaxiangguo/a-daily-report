# LLM Wiki维护与路由契约

## 定位

这个节点约束本仓库的 LLM Wiki 如何吸收外部资料、如何被 AI 引用、如何把一次性问答沉淀成长期知识。

核心原则来自两条经验：

- Karpathy 路线：原始资料先保真归档，LLM 维护的是可演化、可互链、可复盘的 markdown 知识层。
- skill-like 路线：每个知识节点要写清适用场景和不适用场景，让 AI 先判断该不该读，再读取正文。

本仓库不把 LLM Wiki 做成单纯搜索引擎。搜索和 RAG 可以作为局部查证工具，但长期价值来自节点更新、互链、反证和复盘校准。

## 目录分工

- `wiki/资料库/`：只保存来源索引、原文位置、外部材料摘要和查证路径，不直接进入日报主链。
- `wiki/交易思想/`：保存稳定交易原则、认知原则、方法论和可复用判断字段。
- `wiki/板块补充/`：保存板块、主线、产业链、扩散和持续性的可复用框架。
- `wiki/个股分析/`：保存个股结构观察模板和复盘字段。
- `wiki/运行契约/`：保存 AI 使用 wiki、日报生成、数据源、事实入库等可执行约束。

如果外部材料只是启发，先进入 `wiki/资料库/` 或相关节点的 `待核实`；只有经过复述、对比、反证和样本校准后，才进入正式交易节点。

## 来源保真

外部材料进入 LLM Wiki 前，先保存来源，再提炼知识。原文事实、整理判断和待核实推论要分开写，不能把外部启发直接改写成已经确认的交易规则。

- 每份资料至少记录 URL 或本地路径、标题、作者或发布方、发布时间、采集日期和必要上下文。
- 能保存原文位置时，优先在 `wiki/资料库/` 写来源索引；正式知识节点只引用与当前判断相关的来源摘要。
- 来源已经失效或只能部分访问时，写清缺口，不用二手概括冒充原文。
- 引用来源时保留 `source_date`、`capture_date`、`local_path` 或等价字段，方便后续复盘时区分当时事实和后来整理。
- 一条来源可以对应多个知识节点，但每个节点都要说明自己从这份资料中承接了什么、不承接什么。

## 节点最小结构

新增或大改知识节点时，默认包含这些字段。已有节点不强制补齐，但下次维护时逐步补上。

```markdown
# 节点标题

## 定位

这个节点解决什么问题，不解决什么问题。

## 适用场景

- 什么时候该读这个节点。
- 哪类用户问题、日报段落、复盘问题会触发它。

## 不适用场景

- 哪些问题看起来相似，但不该使用这个节点。
- 哪些场景需要回到数据源、原文或其他节点。

## 路由提示

- 触发这个节点的关键词、问题类型或日报段落。
- 容易误触发但应该排除的相似说法。

## 核心判断

- 已确认、可复用的结论。

## 判断规则

- 可以被下一次日报、问股、复盘重复执行的规则。

## 反证与失效

- 什么事实出现时，这个判断不成立。

## 来源与证据

- 原文、报告、复盘、对话或数据来源。

## 待核实

- 还不能写成正式结论的部分。
```

## 摄入流程

处理外部文章、论坛经验、代码片段、交易复盘或长对话时，先做知识编译，不急着生成最终答案。

1. 保留来源：记录 URL、文件路径、日期、作者或上下文，能落到原文位置就不只写二手概括。
2. 建立来源卡：在 `wiki/资料库/` 或目标节点的 `来源与证据` 中写清来源字段、原文位置和可访问状态。
3. 提炼主题：先列出这份资料可能形成哪些知识节点，只写标题、适用场景和使用方式。
4. 补漏检查：检查有没有小但常用的主题被漏掉，新增候选节点，不重复堆同义标题。
5. 挂回原文：把候选节点对应的原文片段、数据样本或复盘事实写到 `来源与证据`。
6. 合并入库：已有节点能承接就更新已有节点，只有主题确实独立时才新建。
7. 写清边界：每次沉淀都必须写 `不适用场景`、`反证与失效` 或 `待核实` 中至少一个。
8. 更新入口：如果节点会被后续 AI 经常引用，同步更新 `wiki/README.md` 的使用方式。

## 提问路由流程

回答用户问题、生成日报、做盘中问股或复盘时，先做轻量路由，再读取正文。

1. 先读 `wiki/README.md`，用其中的使用方式选候选节点。
2. 根据问题意图选择 1 到 5 个最相关节点；优先看 `适用场景`、`不适用场景` 和 `路由提示`，不要因为关键词相似就扩大读取范围。
3. 读取候选节点后，先判断是否真的适用；不适用就回到 README 或来源索引重新选。
4. 需要逐字事实、历史出处或原始上下文时，再通过 `wiki/资料库/` 或原始路径查证。
5. 输出时只带当前问题需要的字段化结论，不把整段理论搬进日报或问股回答。
6. 若回答产生了可复用新规则，先标为待确认；经过样本校准后再写入正式节点。

## 回答反哺规则

一次回答只有满足至少一个条件，才值得反哺 LLM Wiki：

- 以后会反复遇到同类问题。
- 它修正了旧节点的误用边界。
- 它把一次交易复盘拆成了价格事实、当时判断、实际偏差、可复用规则、下次动作。
- 它发现两个已有节点之间的新关系。
- 它指出某个旧结论的反证或失效条件。

不反哺这些内容：

- 当天涨跌、临时情绪、无复盘价值的聊天记录。
- 没有来源、没有反证、没有下次动作的顺口判断。
- 只为一次回答服务的长摘要。
- 可以直接由代码、数据库或 replay 产物计算出来的事实。

反哺时优先更新现有节点的 `适用场景`、`不适用场景`、`反证与失效`、`来源与证据` 或 `待核实`。只有现有节点无法承接新的稳定主题时，才新建节点；新建后同步检查 README 是否需要新增入口。

## 需求变更与日报伴随文档

当一次需求变更会改变日报生成、明日标的选择、持仓继承、数据源、日志、测试或 LLM Wiki 路由时，不能只改代码或只改日报正文。每次变更和每次生成日报，都要同步生成四个伴随文件：`AGENTS.md`、`flow.md`、`testing.md`、`readme.md`，作为项目内伴随文档契约；这里的 `AGENTS.md` 指本次产物的协作说明，不表示自动修改 Codex 全局配置。

日报生成时，四个文件落在报告同目录的伴随目录：正式产物使用 `reports/<日期>_A股日报_伴随文档/`，replay 产物使用 `reports/replay/<日期>_A股日报_伴随文档_replay/`。不要写到项目根目录，避免覆盖项目级协作说明。

- `AGENTS.md`：写清本次变更对协作边界、禁用说法、数据源、交易口径或执行纪律的影响；若不需要改现有项目说明，也要在变更记录中说明“不改”。
- `flow.md`：写清从输入、数据源、筛选、风险复核、唯一明日动作到渲染的流程变化；涉及选股时必须能回答“为什么选中它、为什么没选别人、在哪一步退出”。
- `testing.md`：写清最小验证命令、覆盖的规则、未覆盖风险和人工复核点；日报生成失败时要能从这里追到日志和关键检查。
- `readme.md`：写给下次使用者看的入口说明，说明什么时候触发这套变更、如何复用、如何避免误用。

日报生成本身若没有改变规则，四个文件可以写成简短版本，但不能省略；一旦生成结果暴露出新规则、新 bug 或新口径，必须在四个文件中补齐边界、流程、验证和入口说明后再沉淀到 LLM Wiki。

## 和本地检索/RAG 的关系

本仓库可以在局部使用 `rg`、全文搜索或向量检索，但它们只负责找材料，不负责决定知识是否成立。

- 先由 README 和节点适用场景做知识路由。
- 再在被选中的节点或来源范围内做局部检索。
- 最后由节点的判断规则、反证条件和来源证据共同约束回答。

如果检索结果与 wiki 节点冲突，不能直接覆盖节点；先记录冲突来源、发生日期、适用范围，再决定是更新节点、写入待核实，还是保留旧结论。

## 质量检查

维护 wiki 后，至少检查这些项：

- 新节点是否有适用场景和不适用场景。
- 路由提示是否能帮助 AI 选中正确节点，也能排除相似但不适用的问题。
- 新结论是否能追到来源或复盘样本。
- 来源字段是否能区分原文事实、整理判断和待核实推论。
- 是否误把外部启发写成了已经确认的交易规则。
- 是否把一次性答案塞进了正式知识节点。
- 是否需要更新 `wiki/README.md` 的使用方式。
- 本地检索或 RAG 是否只用于找材料，没有替代节点判断。
- 是否触碰日报主链；如果触碰，必须另走代码和测试验证。

核心判断：LLM Wiki 的质量不看文件数量，而看下次回答是否更容易找到正确节点、更少误用旧结论、更能保留必要认知摩擦。
